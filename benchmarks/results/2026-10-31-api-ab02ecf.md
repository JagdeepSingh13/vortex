## Notes on these results

- **It keeps up at both rates.** Applied trades in each 60 s window match what the engine produced in that time (5,000 orders/s gives ~2,400 trades/s), with 0 duplicates and 0 rejected. Batches grow with load (4 → 9–12 trades), so Redis time per trade falls: pipelining amortises the round trip.
- **Typical latency is ~11–21 ms**, from the engine's event time to the trade being in Redis. That covers the engine's Kafka publish (linger up to 5 ms, acks=all), the consumer's poll and the Redis pipeline. Redis itself is ~2.5–5.5 ms per batch here.
- **Tails vary a lot between identical runs** (5,000/s p99: 699 ms vs 109 ms), the same laptop behaviour as the M5 engine benchmark. With 8 containers on 6 cores in a WSL2 VM, a few short stalls dominate p99 and above.
- **Earlier attempts on the same day, not kept:** the first harness version measured a JVM restarted 10 s earlier and gave p90 of 0.1–7 s. Two causes were found: (1) JIT warm-up: re-running against the already-warm api gave p50 9.3–9.9 ms and p99 72–78 ms at 2,000/s, so the harness now does one unmeasured 60 s warm-up run after starting the api; (2) a Docker VM stall at 18:00:16 UTC in which Kafka's broker heartbeat to its own KRaft controller timed out, so consumers saw `NOT_COORDINATOR` for several seconds. There were no such timeouts in this run.
