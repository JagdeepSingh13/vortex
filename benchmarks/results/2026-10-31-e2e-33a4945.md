## Notes on these results

- **The load generator, not the engine, set the ceiling.** At targets of 20,000 and 30,000 orders/s
  the Python simulator only managed 11,750–17,934/s on average while sharing the laptop with Kafka and
  the engine (alone it reaches 32k–46k/s, M4). The engine kept up throughout: ingest p50 stayed at
  about 5 ms at every rate.
- **Coordinated omission in the generator:** latency starts at the order's `client_time_ns`, stamped
  when the simulator actually builds the message. When the simulator falls behind its schedule, the
  waiting it should have done is not counted, so the 20k/30k rows understate what a client sending
  on schedule would have seen.
- **p50 is stable, p99 is not.** p50 sits at 10–16 ms from 5,000/s upward; p99 varies 3–8x between
  two runs at the same rate (10k/s: 32 vs 266 ms). That spread is this machine (everything in Docker
  in a WSL2 VM under Windows), so only p50 and the best-run p99 are worth quoting.
- **1,000/s is slower than 5,000/s** (p50 16–24 ms vs ~12 ms). Not investigated; a likely cause is
  CPU power saving: at low load the cores idle into deeper sleep states and wake slower. Treat as a
  hypothesis.
- The table header shows commit `b3e5728` while the file name says `33a4945`: a docs-only commit
  landed while the benchmark ran. Engine, simulator and infra code are identical in both.
