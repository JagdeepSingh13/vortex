# 2. Make, CMake and Ninja

Three build tools with three different jobs. They are easy to confuse because two of them have "make" in the name.

| Tool | Job | Where it is configured |
|---|---|---|
| **GNU Make** | The project's **front door**. Short commands (`make engine`) that run longer commands for you. | [Makefile](../../Makefile) at the repo root |
| **CMake** | A **build generator**. Reads a description of the C++ project and writes low-level build instructions. | [engine/CMakeLists.txt](../../engine/CMakeLists.txt) |
| **Ninja** | A **build executor**. Runs those instructions (call the compiler, link) and only redoes what changed. | `build/engine-release/build.ninja`, generated by CMake. Never edit it. |

```
you ──▶ make engine ──▶ docker run ──▶ cmake (generate) ──▶ ninja (compile + link) ──▶ g++
         (Makefile)      (container)    CMakeLists.txt        build.ninja
```

Make could compile C++ by itself, but CMake + Ninja are the standard for C++ projects: CMake handles compilers, flags and libraries portably, and Ninja is faster than Make at the actual compiling. We use Make only as a friendly front door for the whole repo (it will also start Kafka, run the simulator, run dbt, ...).

## What `make run-sim` actually does

Make targets can depend on other targets. In the Makefile:

```make
run-sim: engine          # run-sim needs engine first
engine: engine-image     # engine needs the image first
```

So `make run-sim` runs, in order:

1. **`engine-image`**: `docker build ...` makes sure the toolbox image exists. Cached after the first time, about 1 second.
2. **`engine`**: one throwaway container runs
   ```bash
   cmake -G Ninja -DCMAKE_BUILD_TYPE=Release -S engine -B build/engine-release
   cmake --build build/engine-release
   ```
3. **`run-sim`**: a second throwaway container runs the compiled `simulation`.

Try `make -n run-sim`: `-n` prints the commands without running them. `make help` lists every target with its description.

## The CMake step, flag by flag

```bash
cmake -G Ninja -DCMAKE_BUILD_TYPE=Release -S engine -B build/engine-release
```

| Part | Meaning |
|---|---|
| `-G Ninja` | Generate Ninja instructions (instead of Makefiles or a Visual Studio solution) |
| `-DCMAKE_BUILD_TYPE=Release` | Optimised build, see below |
| `-S engine` | Source folder: where `CMakeLists.txt` lives |
| `-B build/engine-release` | Build folder: where all output goes. Keeping it separate from the source is called an **out-of-source build**: deleting `build/` resets everything safely. |

What `CMakeLists.txt` declares (simplified):

| Target | Kind | Built from |
|---|---|---|
| `cpp_exchange` | Header-only library (`INTERFACE`): just include paths and flags | `src/` |
| `exchange` | Program: the TCP exchange server | `src/exchange_main.cpp` |
| `simulation` | Program: engine + bots in one process | `tools/simulation.cpp` |
| `liquidity_bot`, `trader_terminal` | Programs: TCP clients | `tools/*.cpp` |
| `engine_smoke_test` | Test program, registered with `add_test` | `tests/engine_smoke_test.cpp` |

Compiler flags set for every target: `-std=c++20 -Wall -Wextra -Wpedantic -fno-exceptions`.
- `-Wall -Wextra -Wpedantic`: turn on most warnings.
- `-fno-exceptions`: C++ exceptions are disabled. That is common in low-latency code, which is why the test uses a small `CHECK` macro instead of a framework that throws.

## Release vs Debug

| | Debug | Release (what we use) |
|---|---|---|
| Optimisation | None (`-O0`) | Full (`-O3`) + `-DNDEBUG` |
| Speed | Slow | Fast |
| Debugger | Variables visible, steps line by line | Code reordered, variables "optimised out" |
| `assert()` | Active | Removed |
| Use for | Finding bugs | Running, benchmarking |

Benchmarks must always use Release; measuring a Debug build is a classic mistake. In M2 we will probably add a Debug + sanitizer build for tests.

## Why the build is incremental (and why yours rebuilt everything once)

Ninja keeps a record of every output file and what it was built from. For each step it asks: **is any input newer than the output?**

```
engine/tools/simulation.cpp     modified 23:10
build/.../simulation.cpp.o      built    23:05   → older → recompile
```

It also tracks header files: change `order_book.h`, and everything that includes it is rebuilt.

When you first ran `make run-sim`, all 10 steps ran (`[1/10]` to `[10/10]`). The reason: while setting up git I re-imported the engine folder, which gave every source file a fresh timestamp, newer than the old binaries. Since then nothing has changed, so the next `make engine` prints:

```
ninja: no work to do.
```

CMake also re-runs its configure step each time (`-- Configuring done`), but that is quick and harmless.

## That long yellow warning

```
trader_terminal.cpp:285: warning: '...id...' may be used uninitialized [-Wmaybe-uninitialized]
```

How to read it:
- **File and line**: `trader_terminal.cpp:285`, a client tool, not the engine.
- **What**: GCC thinks a `std::optional<std::uint64_t>` called `id` might be read before it holds a value.
- **The "In member function ... inlined from ..." chain**: the optimiser inlined several functions into `main`, and the warning shows the whole path. That is why it is so long.

The code checks the optional before using it, so this is a **false positive**. `-Wmaybe-uninitialized` is known to fire wrongly on `std::optional` in GCC 12/13 at `-O3`. It is still worth cleaning up (warnings that everyone ignores hide real ones). That is planned for M2.

## Running the tests

```bash
make test
```

runs `ctest`, CMake's test runner, which executes every program registered with `add_test` and reports pass/fail by exit code:

```
1/1 Test #1: engine_smoke_test ......   Passed    0.06 sec
100% tests passed, 0 tests failed out of 1
```
